## 勝ち筋（プレゼンゲーとして）
1. **「友人の農家」という実在の人から始める。** 数字より先に、誰が困ったかを言う
2. **主張は 1 つに絞る。** 「風は雨の補正係数。掛け算で倒れる」。それ以外は脇役
3. **失敗を成果にする。** SAR で見えなかった理由まで確かめたのは、統計に誠実だという証拠
4. **グラフは 1 枚で伝わるものを。** 横軸=雨、縦軸=風、点=嵐、色=倒れた/倒れない、境界線
5. **最後は農家の手元に戻る。** 通知か LED で「今回は危険」と出る一場面

## 台本の骨子（話す順の見出しだけ。本文は結果が出てから）

1. 掴み: 「去年（★今年）、友人の稲が倒れました」。短く、情景で
2. 課題: 事後にしか分からない。統計は粗い。倒れなかった記録がない
3. 方法の一文: 「NASA の衛星と気象データで、3 つの問いを立てました」
4. 失敗: 衛星は見えなかった。なぜ見えないかまで確かめた
5. 発見: 雨と風の関係。散布図 1 枚
6. 仮説と検定: 掛け算（交互作用）。★結果
7. 出口: 小さな端末で動く
8. 呼びかけ: 倒れなかった嵐の記録を

詳しい理由は `docs/design-principles.md`（ベンダーロックイン回避、OSS で永続利用、高価な計算資源を求めない）。

## 想定質問と答え（Q&A 対策）

手法として一般化する主張（`docs/product-direction.md`）を置くので、「他の地域・作物でも検証したか」は必ず聞かれる。答えは「今回は 1 ケース。設計上の主張で、検証は次の一歩」。

| 質問 | 答えの方針 |
|---|---|
| 正例が 3 つでは少なすぎないか | その通り。だから Firth 補正・ベイズ・交差検証を使い、「有意でない」は「分からない」と表現する。次の一歩が「倒れなかった」記録集めなのもそのため |
| 冠水と倒伏は区別できているか | 大雨型の 2 つは冠水も同時。完全には切り分けきれていない。2019-09 の暴風型は冠水が無く、別機構として分けて扱う |
| なぜ衛星で検出できなかったのか | C バンドは田の水・中干し・収穫の影響が大きい。NISAR（L バンド）は茎まで届くので有望だが、今回は時間内に検証できていない（★ここは実状に合わせる） |
| POWER の風は使えないのか | 台風の突風を再現できない（6.9 m/s vs 45.8 m/s）。アメダスで補った。ここは粗い再解析の限界として正直に言う |
| 他の地域・作物に使えるか | 倒伏指数は物理的な形（風²×（1+雨・土壌水分の効果））なので、係数を替えれば適用できる。品種・肥料で係数が変わるはず |
| なぜクラウドにしないのか | `docs/design-principles.md` を参照。ロックインを避け、OSS で永続的に使え、農家に計算コストを負わせない |
| 農家は本当に使うか | まず友人 1 人で検証する。通知は「危険度 3 段階」程度に絞る。マイコンは通信できない田んぼでも動く |
| NASA のデータをどこで使ったか | POWER（気温・土壌水分・日射）、Sentinel-1/HLS/NISAR の検討、NASADEM（標高）。★実際に使ったものだけを書く |
